توجه

کتابخونه های جاوا در زبان برنامه نویسی کاتلین هم قابل استفاده هستن و این مطلب از این قائده مستثنی نیست بنابراین مثال های این مطلب علاوه بر جاوا با کاتلین هم زده شده است؛ و باید به این نکته هم توجه کرد که کاتلین علاوه بر اینکه از کتابخونه های چندنخی جاوا میتونه استفاده کنه، یک کتابخونه ی اختصاصی براش وجود داره به نام کروتینز (Coroutines) که بر اساس چندنخی در جاوا پیاده سازی شده است.

مفهوم رقابت بین نخ ها (race condition) و همگام سازی (synchronizing)

زمانی که چند نخ به طور همزمان بخوان یک داده رو تغییر بدن، هنگام ایجاد تغییرات روی داده ممکنه باعث خراب شدن داده بشن و اصطلاحا میگیم data corruption رخ داده، فرض کنید میخوایم یک متغیر رو با دو عدد به طور همزمان جمع کنیم، برنامه نمیدونه کدوم عدد رو اضافه کنه و ممکنه به طور تصادفی عدد اول رو با متغیر جمع کنه و از عدد دوم صرف نظر کنه، شایدم برعکس عدد دوم رو با متغیر جمع بزنه، به این وضعیت در چندنخی (multithreading) وضعیت رقابت بین نخ (Thread) ها (race condition) یا تداخل نخ (thread) ها میگیم.

در مثال زیر میخوایم امتیاز حساب یک دانش آموز رو به ۱۰۰ برسونیم و برای اینکار از چندنخی استفاده می کنیم.

public class StudentAccount{

  private static Account account = new Account();

      public static void main(String[] args) {

          ExecutorService service = Executors.newCachedThreadPool();

          for (int i=0; i<100; i++){
              service.execute(new IncrementScoreByOne());
          }

          service.shutdown();

          while (!service.isTerminated());

          System.out.println("student score is " + account.getScore());
      }


      private static class IncrementScoreByOne implements Runnable{
          @Override
          public void run() {
              account.updateScore(1);
          }
      }

      private static class Account{
          private Integer score = 0;

          public void updateScore(int v){
              int newScore = score + v;
              try {
                  Thread.sleep(5);
              }catch (InterruptedException e){
                  throw new RuntimeException(e);
              }

              score = newScore;
          }

          public int getScore() {
              return score;
          }
      }
  }
        
private val account = Account()

fun main() {
    val service = Executors.newCachedThreadPool()

    for (i in 1..100) {
        service.execute(IncrementScoreByOne())
    }

    service.shutdown()

    while (!service.isTerminated);

    println("The student score is " + account.score)
}

private class IncrementScoreByOne : Runnable {
    override fun run() {
        account.updateScore(1)
    }
}

private class Account {

    var score: Int = 0
        private set

    fun updateScore(v: Int) {

        val newScore = score + v

        try {
            Thread.sleep(5)
        } catch (e: InterruptedException) {
            throw RuntimeException(e)
        }

        score = newScore

    }
}

در مثال بالا برای بهتر مشخص شدن مشکل از متد (تابع) sleep استفاده کردیم، بعد از اجرای کد میبینیم یک سری اعداد پرت و پلا نشون میده که از ۱۰۰ کمترن علت این موضوع بخاطر تغییر دادن مقدار فیلد score به صورت همزمان توسط چند نخ است.

برای جلوگیری از این وضعیت باید هنگام استفاده از یک داده توسط نخ (thread)، تا پایان کار جلوی دسترسی نخ های دیگه به داده رو بگیریم و اصطلاحا داده رو قفل کنیم، که بهش همگام سازی داده با نخ ها (thread synchronization) میگیم.

داده (متغیر) های volatile

دوتا نخ به نام های A و B رو در نظر بگیرید، فرض کنید این دو نخ دارن یک کار روی داده ی مشترک انجام میدن، زمانی که تغییرات توسط نخ A روی داده انجام میشه این تغییرات توسط نخ B فورا خونده نمیشه علتش بخاطر اینه که زمانی که داده توسط نخ A دچار تغییر میشه تغییرات روی حافظه ی موقت (RAM) ذخیره بشه، روی حافظه ی پنهان (cache) پردازنده میاد و نخ B به تغییرات نخ A روی cache پردازنده دسترسی نداره.

برای اینکه تغییرات یک نخ روی داده توسط نخ های دیگه فورا خونده بشه از volatile در جاوا و کاتلین استفاده می کنیم؛ با استفاده از volatile تغییرات بجای حافظه ی پنهان (cache) پردازنده، مستقیم تو حافظه ی موقت (RAM) ذخیره میشن و سایر نخ ها به این تغییرات دسترسی دارن.

هنگام استفاده از volatile، مشکل دسترسی همزمان نخ ها به داده حل نمیشه، ولی تغییرات روی داده توسط یک نخ فورا قابل خوندن توسط نخ های دیگه است.

زمانی که بخوایم بقیه ی نخ (thread) ها از تغییرات در داده توسط یک نخ با خبر بشن، داده رو با volatile تعریف میکنیم.

زمانی که فقط نیاز به flag داریم تا وضعیت داده رو بین نخ ها مشخص کنیم، فیلد رو با volatile تعریف می کنیم، زمانی که مشکل برنامه با volatile حل میشه بهتره جایگزین استفاده از قفل ها در برنامه بشه که در ادامه بهشون می پردازیم، استفاده از volatile بهینه تره.

در جاوا متغیر رو با volatile تعریف می کنیم و در کاتلین با @Volatile

در مثال زیر هردو کار TaskA و TaskB منتظر اجازه ی کاربر هستند، زمانی که کاربر y یا yes رو وارد کنه هردو کار TaskA و TaskB پیام رو نمایش میدن.

public static void main(String[] args){
    Permission permission = new Permission();

    ExecutorService service = Executors.newFixedThreadPool(3);
    service.execute(new TaskA(permission));
    service.execute(new TaskB(permission));
    service.execute(new UserInputPermissionTask(permission));

    service.shutdown();
}

private static class Permission {
    private volatile boolean granted;
}

private static class TaskA implements Runnable {
    private Permission permission;

    public TaskA(Permission permission) {
        this.permission = permission;
    }

    @Override
    public void run() {
        while (!permission.granted) ;

        System.out.println("A message from TaskA");
    }
}

private static class TaskB implements Runnable{
    private Permission permission;

    public TaskB(Permission permission){
        this.permission = permission;
    }

    @Override
    public void run() {
        while (!permission.granted);

        System.out.println("A message from TaskB");
    }
}

private static class UserInputPermissionTask implements Runnable{

    private Permission permission;

    public UserInputPermissionTask(Permission permission){
        this.permission = permission;
    }


    @Override
    public void run() {
        Scanner input = new Scanner(System.in);

        while (true) {
            System.out.println("Ask permission: Do u wanna print message?(yes/no)");
            String userInput = input.next();
            if (userInput.equalsIgnoreCase("y") || userInput.equalsIgnoreCase("yes")) {
                permission.granted = true;
                System.out.println("Permission Granted!");
                break;
            }
            else {
                System.out.println("Permission Denied!");
            }
        }
    }
}
        
fun main() {
    val permission = Permission()

    val service = Executors.newFixedThreadPool(3)
    service.execute(TaskA(permission))
    service.execute(TaskB(permission))
    service.execute(UserInputPermissionTask(permission))

    service.shutdown()
}


private class Permission {
    @Volatile
    var granted = false
}

private class TaskA(private val permission: Permission) : Runnable {
    override fun run() {
        while (!permission.granted);

        println("A message from TaskA")
    }
}

private class TaskB(private val permission: Permission) : Runnable {
    override fun run() {
        while (!permission.granted);

        println("A message from TaskB")
    }
}

private class UserInputPermissionTask(private val permission: Permission) : Runnable {
    override fun run() {
        val input = Scanner(System.`in`)

        while (true) {
            println("Ask permission: Do u wanna print message?(yes/no)")
            val userInput = input.next()
            if (userInput.equals("y", ignoreCase = true) || userInput.equals("yes", ignoreCase = true)) {
                permission.granted = true
                println("Permission Granted!")
                break
            } else {
                println("Permission Denied!")
            }
        }
    }
}

در بالا اگه متغیر granted با volatile تعریف نمیشد هردوکار TaskA و TaskB متوجه تغییرات در مقدار granted توسط UserInputPermissionTask نمیشدن.

داده ای که با volatile تعریف شده رو میتونیم با یک نخ تغییر بدیم و سپس با چند نخ به طور همزمان تغییرات رو بخونیم اما نمیتونیم همزمان با چند نخ داخل داده تغییر ایجاد کنیم، بنابراین volatile مشکل رقابت بین نخ ها رو حل نمیکنه

اگه مثال StudentAccount رو بخوایم با volatile حل کنیم مشابه زیر میشه.

public class StudentAccountVolatile {
    private static final Account account = new Account();

    public static void main(String[] args) {

        ExecutorService service = Executors.newCachedThreadPool();

        while (account.getScore() != 100)
            service.execute(new IncrementScoreByOne());

        service.shutdown();

        while (!service.isTerminated()) ;

        System.out.println(account.getScore());
    }

    private static class IncrementScoreByOne implements Runnable{

        @Override
        public void run() {
            if (account.getScore() != 100)
                account.updateScore(1);
        }
    }

    private static class Account {
        private volatile Integer score = 0;

        public void updateScore(int v) {
            int newScore = score + v;
            try {
                Thread.sleep(5);
            } catch (InterruptedException e) {
                throw new RuntimeException(e);
            }

            score = newScore;
        }

        public int getScore() {
            return score;
        }
    }
}
        
private val account = Account()

fun main() {
    val service = Executors.newCachedThreadPool()

    while (account.score != 100) service.execute(IncrementScoreByOne())

    service.shutdown()

    while (!service.isTerminated);

    println(account.score)
}

private class IncrementScoreByOne : Runnable {
    override fun run() {
        if (account.score != 100) account.updateScore(1)
    }
}

private class Account {
    @Volatile
    var score: Int = 0
        private set

    fun updateScore(v: Int) {
        val newScore = score + v
        try {
            Thread.sleep(5)
        } catch (e: InterruptedException) {
            throw RuntimeException(e)
        }

        score = newScore
    }
}

با توجه به منطق کد باید انتظار داشته باشیم 100 نخ (thread) ایجاد بشه اما مقدار نخ های ایجاد شده بیشتر از 100 خواهد بود و این امر بخاطر اینه ممکنه چندتا نخ بخوان به طور همزمان مقدار score رو افزایش بدن، رو افزایش بدن چندتا نخ اجرا میشه ولی فقط یک واحد به score اضافه میشه، چون تداخل وجود داره و با توجه به شرط برنامه اگه مقدار score به 100 نرسیده باشه، نخ هایی ایجاد میشن که بخاطر تداخل باهم، مقدار score رو فقط یک واحد افزایش میدن؛ پس ممکنه تا قبل از اینکه مقدار score به 100 برسه بعضی نخ (thread) ها تلف بشن.

با اینکه با volatile مشکل تا حد زیادی حل شده، ولی همین تداخل ممکنه باعث بشه گاهی هرچند به ندرت خطا هم وجود داشته باشه، مثلا به 100 نرسه و تا 99 یا 98 کار تموم بشه.

یک راه حل بهتر برای حل 100 درصدی مشکل رسیدن score به 100 وجود داره اونم استفاده از قفل هاست، قفل ها رو میتونیم با synchronized یا با کلاس ReentrantLock ایجاد کنیم که در ادامه بهش میپردازیم.

همگام سازی با synchronized

همگام سازی در چندنخی یعنی هماهنگ کردن اجرای نخ هایی که به هم وابسته هستن.

برای جلوگیری از race condition میتونیم از synchronized برای همگام سازی آبجکت یا متد استفاده کنیم، زمانی که از synchronized استفاده بشه، تنها یک نخ میتونه به داده دسترسی داشته باشه و تا زمانی که کار نخ (thread) تموم نشده داده قفل میمونه و نخ های دیگه به داده دسترسی ندارن.

از کلیدواژه ی synchronized میتونیم برای همگام سازی آبجکت و متد در جاوا استفاده کنیم و همینطور برای همگام سازی تابع در کاتلین از @Synchronized و برای همگام سازی آبجکت در کاتلین از تابع خطی (inline function) synchronized استفاده کنیم.

استفاده از synchronized برای همگام سازی آبجکت

با استفاده از synchronized میتونیم یک قفل روی آبجکت ایجاد کنیم تا هنگام استفاده از آبجکت توسط چند نخ (Thread) دچار race condition نشیم.

فرم کلی:

synchronized (expression){
   //statement
}
          
synchronized(lock: Any, block: () -> R)

بجای expression متغیری که به آبجکت اشاره می کنه رو می نویسیم و داخل بلوک توابع یا فیلد های آبجکت رو که میخوایم قفل بشن صدا میزنیم.

در مثال StudentAccount میتونیم یک عبارت synchronized برای account تعریف کنیم و از race condition جلوگیری کنیم.

private static class IncrementScoreByOne implements Runnable{
    @Override
    public void run() {
        synchronized (account) {
            account.updateScore(1);
        }
    }
}
          
private class IncrementScoreByOne : Runnable {

    override fun run() {
        synchronized(account, fun(){
            account.updateScore(1)
        })
    }
}

استفاده از synchronized برای همگام سازی متد (تابع)

تابع برای نخ های دیگه ازاد نمیشه و نخ های دیگه نمیتونن تابع رو اجرا کنن، به متد هایی که با synchronized تعریف میشن، متد های همگام سازی شده (Synchronized Methods) گفته میشه.

در مثال قبل برای اینکه race condition به وجود نیاد کافیه متد (تابع) updateScore رو با synchronized تعریف کنیم.

private static class Account{
  private Integer score = 0;
  public synchronized void updateScore(int v){
      int newScore = score + v;
      try {
          Thread.sleep(5);
      }catch (InterruptedException e){
          throw new RuntimeException(e);
      }
      score = newScore;
  }
  public int getScore() {
      return score;
  }
}
        
private class Account {

    var score: Int = 0
        private set

    @Synchronized
    fun updateScore(v: Int) {
        val newScore = score + v
        try {
            Thread.sleep(5)
        } catch (e: InterruptedException) {
            throw RuntimeException(e)
        }

        score = newScore
    }
}

از این به بعد زمانی که گفته میشه یک متد در جاوا synchronized است باید بدونید منظور چیه :)

همکاری بین نخ (Thread) ها با متد های wait, notify و notifyAll

نخ (thread) ها میتونن باهمدیگه همکاری کنن، دوتا نخ رو در نظر بگیرید زمانی که اجرای نخ اول به جایی برسه، نخ اول متوقف بشه و نخ دوم شروع به کار کنه و زمانی که اجرای نخ دوم به جایی برسه، نخ دوم متوقف بشه و نخ اول شروع به کار کنه.

برای بدست اوردن چنین عملکردی در کلاس Object جاوا سه متد (تابع) به نام های wait, notify و notifyAll تعریف شده، از این سه تابع میتونیم داخل متد هایی که با synchronized تعریف شده باشن یا عبارت synchronized استفاده کنیم.

توجه

استفاده از سه متد wait, notify و notifyAll فقط در جاهایی که synchronized تعریف شده امکان پذیر است.

متد (تابع) wait

از این متد (تابع) برای متوقف کردن نخ هایی که دارن از آبجکت مورد نظر استفاده میکنن، استفاده کنیم؛ و برای ادامه ی کار نخ منتظر سیگنال ادامه میمونه.

متد (تابع) notify

اگه یک نخ توسط یک آبجکت با wait متوقف شده باشه، با استفاده از متد notify میتونیم سیگنال ادامه رو به نخ (thread) بدیم. سیگنال ادامه ی کار فقط به نخ هایی داده میشه که توسط همون آبجکت با wait متوقف شده باشن، و اگه چند نخ توسط آبجکت با wait متوقف شده باشه با notify فقط یکیشون به کار ادامه میده.

متد (تابع) notifyAll

از این متد برای دادن سیگنال به تمام نخ های متوقف شده روی آبجکت فعلی استفاده می کنیم، استفاده از این متد هر نخی که روی این آبجکت متوقف شده باشه رو اجرا می کنه، سیگنال ادامه ی کار به نخ هایی داده میشه که توسط همون آبجکت با wait متوقف شده باشن و تمام نخ های متوقف شده با سیگنال notifyAll به کار خودشون ادامه میدن.

توجه

از اونجایی که متد (تابع) های wait, notify و notifyAll در کلاس Object جاوا تعریف شدن، برای استفاده ازشون تو کاتلین باید کلاس رو به Object کست کنیم.

مثال زیر یک برنامه ی تولید کننده و مصرف کننده است (Consumer-Producer) یک مثال کلاسیک برای درک مفهوم همکاری بین نخ (thread) ها؛ در این مثال یک کلاس داریم و دوتابع به اسم produce و consume، زمانی که مقدار data صفر باشه تابع consume متوقف میشه و سیگنال ادامه ی کار رو به produce می فرسته و تابع produce شروع به کار میکنه تا مقدار داده تغییر کنه، زمانی که مقدار داده تغییر کرد، تابع produce متوقف میشه و سیگنال ادامه ی کار رو به تابع consume میفرسته و consume شروع به ادامه ی کار میکنه.

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class ConsumerProducerDemo {

    public static void main(String[] args) {
        ExecutorService service = Executors.newFixedThreadPool(2);

        ConsumerProducer cp = new ConsumerProducer();

            service.execute(() -> {
                while (true)
                    cp.consume();
            });


            service.execute(() -> {
                while (true)
                    cp.produce();
            });

            service.shutdown();

    }

    private static class ConsumerProducer{
        private int data;


        public synchronized void consume(){
            try {

                while (data == 0) {
                    wait();
                }
                Thread.sleep(1000);
            }catch (InterruptedException e){
                e.printStackTrace();
            }

            System.out.println("Consuming " + data);
            data = 0;
            notify();
        }

        public synchronized void produce(){

            try {
                while (data != 0) {
                    wait();
                }

                Thread.sleep(2000);
            }catch (InterruptedException e){
                e.printStackTrace();
            }

            data = (int) (1 + (Math.random() * 126));
            System.out.println("Producing " + data);
            notify();
        }
    }
}       
        
fun main(){
    val service = Executors.newFixedThreadPool(2)
    val cp = ConsumerProducer()
    service.execute(Runnable {
        while (true) cp.consume()
    })
    service.execute(Runnable {
        while (true) cp.produce()
    })
    service.shutdown()
}

@Suppress("PLATFORM_CLASS_MAPPED_TO_KOTLIN")
private class ConsumerProducer{
    private var data = 0

    @Synchronized
    fun consume() {

        try {
            while (data == 0) {
                (this as Object).wait()
            }
            Thread.sleep(1000)
        } catch (e: InterruptedException) {
            e.printStackTrace()
        }
        
        println("Consuming $data")
        data = 0
        (this as Object).notify()
    }

    @Synchronized
    fun produce() {
        try {
            while (data != 0) {
                (this as Object).wait()

}

همگام سازی با کلاس ReentrantLock

با استفاده از Lock و condition میتونیم به صورت آشکار (explicitly) داده ها رو با نخ ها همگام سازی کنیم.

با synchronized یک قفل پنهانی (implicit lock) روی نمونه قرار میدادیم و هنگام استفاده از متد توسط نخ (thread)، متد برای استفاده از نخ قفل میشد.

با استفاده از کلاس ReentrantLock میتونیم بدون نیاز به synchronized یک متد رو به صورت آشکار (explicitly) قفل کنیم؛ یکی از پیاده سازی های داخل کلاس ReentrantLock، اینترفیس Lock است که متد های پرکاربرد lock, unlock و newCondition داخل اینترفیس lock تعریف شده اند.

توجه

در اکثر موارد استفاده از synchronized کفایت میکنه ولی استفاده از ReentrantLock کنترل بیشتری روی هماهنگ کردن نخ ها به برنامه نویس میده.

در زیر نمودار uml ارتباط ReentrantLock با اینترفیس Lock و متد های پیاده سازی شده ی داخلش شرح داده شده است.

در زیر متد های تعریف شده در اینترفیس Lock اورده شده است.

java.util.concurrent.locks.Lock
+lock(): void یک قفل ایجاد میکنه.
+unlock(): void قفل رو آزاد میکنه.
+newCondition(): Condition یک نمونه از Condition رو بر میگردونه.

اینترفیس Lock در کلاس ReentrantLock پیاده شده است.

java.util.concurrent.locks.ReentrantLock
+ReentrantLock() یک نمونه از کلاس ReentrantLock ایجاد میکنه.
+ReentrantLock(fair: boolean) یک نمونه از کلاس ReentrantLock ایجاد میکنه و زمانی که مقدار پارامتر true باشه و نخی که بیشتر از بقیه ی نخ ها تو صف استفاده از داده قرار گرفته، اولین اولویت استفاده از داده بعد از آزاد شدن داده رو داره.

اینترفیس Condition

هنگام استفاده از کلاس ReentrantLock بجای متد های wait، notify و notifyAll باید از متدهای اینترفیس Condition استفاده کنیم، برای ایجاد یک نمونه از condition کافیه متد newCondition رو با ReentrantLock صدا بزنیم.

<<java.util.concurrent.Condition>>
+await(): void باعث میشه نخ (thread) فعلی به طور موقت متوقف بشه تا وقتی که سیگنال ادامه بهش داده بشه.
+signal(): void به یکی از نخ (thread) های متوقف شده با await سیگنال اجرا میده.
+signalAll(): void به تمام نخ (thread) های متوقف شده با await سیگنال اجرا میده.

میخوایم در مثال زیر یک Buffer رو شبیه سازی کنیم و با دو کار ProducerTask و ConsumerTask مقادیر رو با Buffer نوشته و هنگامی که ظرفیت Buffer پر شد مقادیر نوشته شده رو بخونیم.

در مثال زیر در داخل کلاس Buffer دو نمونه از Condition ایجاد می کنیم یکی برای متد (تابع) write و اون یکی برای متد (تابع) read؛ هنگامی که ظرفیت Buffer پر باشه، با writeCondition متد write رو متوقف میکنیم و داخل متد write با readCondition سیگنال ادامه رو به متد read میدیم تا ظرفیت Buffer با متد read خالی بشه و زمانی که buffer با read خالی شد، داخل تابع read با writeCondition دوباره سیگنال ادامه ی کار write رو رو میدیم و با readCondition کار متد read رو متوقف می کنیم؛ متغیر CAPACITY ظرفیت Buffer و مقدارش ثابت و برابر با 1 است

در زیر به صورت تصویری عملکرد این برنامه شرح داده شده است.

public class ConsumerProducerReentrantLockDemo {

    private static final Buffer buffer = new Buffer();

    public static void main(String[] args) {
        ExecutorService service = Executors.newFixedThreadPool(2);
        service.execute(new ProducerTask());
        service.execute(new ConsumerTask());

        service.shutdown();
    }

    private static class ProducerTask implements Runnable{
        @Override
        public void run() {
            while (true){
                int value = (int)(Math.random() * 256);
                System.out.println("Producer writes " + value);
                buffer.write(value);
                try {
                    Thread.sleep((long)(Math.random() * 10000));
                } catch (InterruptedException e) {
                    throw new RuntimeException(e);
                }
            }

        }
    }

    private static class ConsumerTask implements Runnable{
        @Override
        public void run() {
            while (true){
                int value = buffer.read();
                System.out.println("\t\t\tConsumer reads " + value);
                try {
                    Thread.sleep((int)(Math.random() * 10000));
                } catch (InterruptedException e) {
                    throw new RuntimeException(e);
                }
            }
        }
    }

    private static class Buffer{
        private static final int CAPACITY = 1;
        private final Queue<Integer> queue = new LinkedList<>();

        private final Lock lock = new ReentrantLock();

        private final Condition writeCondition = lock.newCondition();
        private final Condition readCondition = lock.newCondition();

        public void write(int value){
            lock.lock();

            try{
                while (isFull()) {
                    System.out.println("Wait for reading buffer");
                    writeCondition.await();
                }

                queue.offer(value);
                readCondition.signal();
            }catch (InterruptedException e){
                e.printStackTrace();
            }finally {
                lock.unlock();
            }
        }


        public int read(){
            int value = 0;
            lock.lock();
            try {
                while (isEmpty()){
                    System.out.println("\t\t\tWait for writing buffer");
                    readCondition.await();
                }

                value = queue.remove();
                writeCondition.signal();

            }catch (InterruptedException e){
                e.printStackTrace();
            }finally {
                lock.unlock();
            }

            return value;
        }

        private boolean isEmpty(){
            return queue.isEmpty();
        }

        private boolean isFull(){
            return queue.size == CAPACITY;
        }
    }
}

            println("\t\t\tConsumer reads $value")

            }

        }

}

private class Buffer {
    private val queue: Queue<Int> = LinkedList()

    private val lock: Lock = ReentrantLock()

    private val writeCondition: Condition = lock.newCondition()
    private val readCondition: Condition = lock.newCondition()

    private val isEmpty get() = queue.isEmpty()
    private val isFull get() = queue.size == CAPACITY

    fun write(value: Int) {
        lock.lock()

        try {
            while (isFull) {
                println("Wait for reading buffer")
                writeCondition.await()
            }

            queue.offer(value)
            readCondition.signal()
        } catch (e: InterruptedException) {
            e.printStackTrace()
        } finally {
            lock.unlock()
        }
    }


    fun read(): Int {
        var value = 0
        lock.lock()
        try {
            while (isEmpty) {
                println("\t\t\tWait for writing buffer")
                readCondition.await()
            }

            value = queue.remove()!!
            writeCondition.signal()
        } catch (e: InterruptedException) {
            e.printStackTrace()
        } finally {
            lock.unlock()
        }

        return value
    }

        private const val CAPACITY = 1
    }
}

محدود کردن دسترسی تعداد نخ (thread) ها به داده با کلاس Semaphore

با استفاده از کلاس Semaphore در جاوا و کاتلین میتونیم تعداد نخ هایی که به داده میتونن دسترسی داشته باشن رو محدود کنیم، برخلاف synchronized و ReentrantLock که فقط به یک نخ دسترسی به داده رو میدن با Semaphore میتونیم دسترسی به داده رو محدود به یک یا چند نخ کنیم، به عبارتی خودمون تعیین میکنیم که چندتا نخ همزمان میتونه به یک داده دسترسی داشته باشه.

java.util.concurrent.Semaphore
+Semaphore(numberOfPermits) یک نمونه از Semaphore ایجاد می کنه و داخل پارامتر کانستراکتور تعداد نخ هایی که میتونن از داده ها (منابع) استفاده کنن رو تعیین میکنیم.
+Semaphore(numberOfPermits: int, fair: boolean) یک نمونه از Semaphore ایجاد میکنه و تعداد نخ هایی که میتونن از داده (منابع) استفاده کنن رو تعیین میکنیم و همینطور با boolean مشخص میکنیم نوبت دهی منصفانه باشه یعنی نخی که بیشتر از همه منتظر مونده تا از منابع استفاده کنه زمانی که کار یکی از نخ ها تموم بشه اولویت بالاتری نسبت به بقیه داره تا شروع کنه.
+acquire(): void محدودیت استفاده از داده (منابع) رو ایجاد میکنه.
+release(): void محدودیت ایجاد شده رو بر میداره.

مفهوم Deadlock

معلم میره سر کلاس میبینه دانش آموز نیست، دانش آموز میره سر کلاس میبنه معلم نیست، این وضعیت تا زمانی که ادامه پیدا کنه مدرسه تعطیله، بحث Deadlock مشابه همینه دوتا کار در دو نخ جدا به همدیگه وابسته ان، هردو قفل شدن و هرکدوم منتظر اون یکیه تا شروع بشه یا ادامه پیدا کنه.

یکی از کار هایی که ممکنه باعث deadlock بشه صدا زدن notify یا notifyAll توسط یک آبجکت دیگه برای ادامه ی اجرای thread یک آبجکت دیگس.

در مثال ConsumerProducer فرض کنید بجای یک کلاس مشترک برای متد های consume و produce یک کلاس جدا برای consume تعریف کرده باشیم و یک کلاس دیگه برای produce و مانند قسمت قبل میخوایم از wait و notify برای توقف و سیگنال دادن به نخ هاشون استفاده کنیم.

برای جلوگیری از deadlock از روش ترتیب منابع (resource ordering) استفاده کنید هر چیزی که قفل روشه رو به ترتیب با نخ (thread) اجرا کنید و از اجرای قفل های تو در تو پرهیز کنید و همینطور موقع صدا زدن wait و notify دقت کنید که این متد ها پس زمینه ی آبجکتی باشن که داریم از متد هاش استفاده می کنیم.

خلاصه

  • زمانی که چندتا نخ به صورت همزمان دارن از یک داده استفاده میکنن، race condition پیش میاد.
  • زمانی که سایر نخ ها بخوان از وضعیت تغییرات در یک داده ی مشترک توسط یک نخ فورا با خبر بشن، داده رو باید با volatile تعریف کنیم.
  • برای جلوگیری از race condition در جاوا و کاتلین میتونیم از synchronized یا کلاس های ReentrantLock و Semaphore استفاده کنیم.
  • زمانی که از کلاس ReentrantLock استفاده میکنیم بجای wait, notify و notifyAll باید از متد های await, signal و signalAll در اینترفیس condition استفاده کنیم.
  • با استفاده از متد newCondition در Lock میتونیم یک نمونه از Condition استفاده کنیم.
  • با استفاده از کلاس Semaphore میتونیم تعداد نخ هایی که میتونن به یک داده دسترسی داشته باشن رو محدود کنیم.
